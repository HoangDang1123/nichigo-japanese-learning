# JPN-011 — Guest Foundation API Contract

**APPROVED TECHNICAL CONTRACT — BACKEND IMPLEMENTED AND MERGED (PR #35); FRONTEND NOT INTEGRATED; NOT RELEASED**

This document specifies the approved HTTP and persistence boundaries for the **approved product rules** in [ADR-002, ADR-018 and ADR-019](../02-DECISIONS.md). Its baseline and draft wording below record the state before JPN-011 implementation. The [backend implementation note](JPN-011-guest-foundation-backend.md) records the merged backend source and its branch-era test evidence. This contract does not define JPN-012 account claiming, JPN-032 Assessment mechanics, JPN-040 completion or Item mastery. `/api/v1` prefixes all paths below.

## Actor, cookie and CSRF contract — APPROVED

The server issues a cryptographically unpredictable opaque Guest credential in an HttpOnly cookie named `NICHIGO_GUEST`. The credential maps to a stable server-side Guest identity; neither credential nor Guest ID appears in response JSON, URL, request body or JavaScript-readable storage. The server stores a one-way verifier for the credential and resolves the actor on every Guest request. A valid authenticated User session takes precedence over a Guest cookie; the two actors' data are never mixed. Guest-to-account claim is **PENDING OWNER DECISION**. A missing/invalid Guest credential never selects another Guest by client-supplied ID.

The proposed Guest cookie is `Secure` in HTTPS deployment, HttpOnly and scoped to the API; deployment-specific `SameSite`/domain topology remains open. Local HTTP may use the existing development-only insecure setting. The Guest credential and Auth/CSRF `SESSION` have independent lifecycles: the existing `SESSION` can expire after 30 minutes without deleting the Guest identity or server-side learning data. A returning Guest with a valid Guest credential can obtain a new `SESSION`-bound CSRF token through `GET /auth/csrf`, then continue permitted mutations with both cookies and `X-CSRF-TOKEN`. Cookie renewal is specified below as a **technical draft**, not an approved product rule. Guest-to-account claim/merge remains **PENDING OWNER DECISION**.

**Approved retention activity:** Guest data becomes cleanup-eligible 90 days after the Guest last actively used NichiGo. Active opening/use of the site, viewing Kana/Vocabulary/Grammar/Kanji or other eligible Skills, Learning Path/Lesson discovery, Lesson study or restudy, Flashcards, Vocabulary Quick Check, Practice, Assessment and bookmark save/remove qualify. Active viewing of public content counts; a Lesson unlock or data mutation is not required. Background polling, automatic session/token refresh, CSRF bootstrap alone, background prefetch and an idle open tab without real interaction do not qualify. The backend cannot perfectly verify that a person is viewing the screen; the validated activity signal below is retention evidence only and never authorizes content, increases quota or creates learning results. Cleanup timing is not a promise of deletion at exactly midnight.

All proposed state-changing requests, including Guest initialization and idempotent PUT/DELETE, require the existing `SESSION`-bound `X-CSRF-TOKEN` from `GET /auth/csrf`, plus credentials. GET requests do not require a CSRF header. After User login, obtain a fresh CSRF token as current auth behavior requires. The backend must validate the Guest credential and current actor on every request; the frontend cannot authorize access by hiding controls.

## Endpoint specification — APPROVED CONTRACT

`Guest` means a valid server-issued Guest credential and no authenticated User session. `Actor` means either a Guest or authenticated User, resolved only on the server. All success DTOs below are presentation data, not database entities. Path/query/body IDs are selectors, never actor identity or grade/quota authority. All errors use the flat error body in the next section. `204` responses have no body.

| Method and path | Actor; request DTO | Success DTO and behavior | Failure, idempotency and authorization |
|---|---|---|---|
| `POST /guest/session` | Public with CSRF; empty body; existing `NICHIGO_GUEST` cookie if present | `201` for a new Guest, `200` for a valid existing Guest: `{ "actorType":"guest", "restored":boolean }`; sets/retains opaque cookie. A valid existing identity is not duplicated. | Invalid/expired credential: `401 guest_identity_invalid`, clears that cookie; the client may call again without it to start a new Guest. No arbitrary Guest ID input. Authenticated User: `409 actor_conflict`; no implicit claim/merge. |
| `GET /guest/session` | Guest; no body | `200 { "actorType":"guest" }` confirms restoration without exposing the credential or ID. | Missing/invalid credential: `401 guest_identity_invalid`. Repeated GET has no identity or quota side effect. Authenticated User uses `/auth/me`, not this Guest route. |
| `POST /guest/activity` | Guest with `SESSION`-bound CSRF; empty JSON body `{}`; no Guest ID or client timestamp | `200 { "lastActiveAt":"ISO-8601-instant", "retentionEligibleAt":"ISO-8601-instant" }`, calculated by the server. `lastActiveAt` is the last persisted active signal; `retentionEligibleAt` is the conservative earliest cleanup time after accounting for draft write throttling. Records the first active signal immediately; later signals may be write-throttled as described below. Creates no unlock, bookmark, Assessment result or completion. | Missing/invalid/retention-expired Guest credential: `401 guest_identity_invalid`, with no activity update or credential renewal. Missing/invalid CSRF: existing 403 behavior. A repeated valid signal does not change learning/quota state. |
| `GET /guest/quota` | Guest; no body | `200 { "localDate":"YYYY-MM-DD", "timeZone":"Asia/Ho_Chi_Minh", "dailyLimit":2, "used":number, "remaining":number, "resetsAt":"ISO-8601-instant" }`. Date and reset instant are calculated by the backend; no carry-over. | `401 guest_identity_invalid` for absent/expired Guest; repeated GET consumes nothing. User has no Guest quota and does not call this route. |
| `GET /lessons/{slug}/access` | Actor; no body | `200 LessonAccess` (below) for an eligible published Lesson. A Guest's `canStart` reflects current allowance; an already unlocked Lesson remains accessible even at 0 remaining. User access has no Guest quota. | `404 content_not_found` for missing, withdrawn, unpublished or Rights-ineligible Lesson; `401` for missing actor identity. This route returns no full Lesson sections/Items. |
| `GET /learning-paths/{pathSlug}/placements/{placementId}/lesson/access` | Actor; no body | `200 LessonAccess` for the eligible Lesson revision pinned by the current eligible Path placement. | `404 content_not_found` for absent/ineligible Path, placement or pinned Lesson; `401` for missing actor. No full content or client-selected revision. |
| `POST /lessons/{slug}/unlock` | Guest with CSRF; empty body | `200 LessonUnlockResult` (below). First Start Learning authorizes and records the stable Lesson identity, then reports `newlyUnlocked:true`; repeat reports `false`. Both return the updated Guest quota/status. | `403 guest_unlock_quota_exceeded` for a third new Lesson; `404 content_not_found` for ineligible Lesson; `401 guest_identity_invalid`; concurrent retry is idempotent. No full Lesson body is returned by the mutation. A User reads eligible Lessons without this operation. |
| `POST /learning-paths/{pathSlug}/placements/{placementId}/lesson/unlock` | Guest with CSRF; empty body | Same `LessonUnlockResult` for the stable Lesson identity resolved from the current eligible Path placement and its pinned revision. Unlocking the same Lesson through either route counts once. | Same quota/identity rules as independent unlock; `404 content_not_found` for ineligible Path/placement/pinned Lesson. Client cannot choose a revision. |
| `GET /lessons/{slug}` | Actor; no body; **existing route, target authorization change** | Existing `PublicContentDtos.Lesson` shape after checking current publication/Rights and, for Guest, stable Lesson unlock. Independent read resolves current published Lesson revision. | Locked Guest: `403 lesson_not_unlocked` without content; ineligible/missing: `404 content_not_found`; missing/invalid identity: `401`. Never trust a query-supplied revision. |
| `GET /learning-paths/{pathSlug}/placements/{placementId}/lesson` | Actor; no body; **existing route, target authorization change** | Existing Lesson DTO after checking eligible current Path/placement, pinned Lesson revision and Guest unlock of that stable Lesson identity. | Locked Guest: `403 lesson_not_unlocked`; absent/ineligible Path, placement or pinned dependency: `404 content_not_found`; missing/invalid identity: `401`. A Path placement cannot bypass the independent Lesson gate or choose historical revisions. |
| `PUT /skills/bookmarks/{itemId}` | Actor with CSRF; `itemId` is canonical Item UUID; empty body | `200 BookmarkMutation` (below) with `saved:true`, current count/limit/capacity. Duplicate save returns the same saved state without using another slot. | Guest at 20 saving a **new** distinct Item: `403 guest_bookmark_limit_reached`; ineligible Item: `404 content_not_found`; missing actor: `401`; atomic capacity check. User has no product count limit. |
| `DELETE /skills/bookmarks/{itemId}` | Actor with CSRF; empty body | `200 BookmarkMutation` with `saved:false` and updated count/capacity. Never return revoked/unpublished content, media or private Rights evidence. |
| `GET /skills/bookmarks/summary` | Actor; no body | `200 BookmarkSummary` for count/remaining independent of pagination. | `401` without actor; `503 content_unavailable` on failure. GET does not spend capacity. |

**Draft DTOs:** `LessonAccess = { lessonId:UUID, slug:string, accessStatus:"unlocked"|"locked", canStart:boolean, guestQuota:GuestQuota|null }`; `LessonUnlockResult = { lessonId:UUID, slug:string, accessStatus:"unlocked", newlyUnlocked:boolean, guestQuota:GuestQuota }`; `GuestQuota` has the fields of `GET /guest/quota`. `BookmarkSummary = { savedCount:number, maxSaved:number|null, remaining:number|null }`; `BookmarkMutation = { itemId:UUID, saved:boolean, summary:BookmarkSummary }`; `BookmarkStatus = { itemId:UUID, saved:boolean, availability:"available"|"unavailable"|null, summary:BookmarkSummary }`. `SavedEntry` is either `{ itemId:UUID, saved:true, availability:"available", item:EligiblePublicItem }` or `{ itemId:UUID, saved:true, availability:"unavailable" }`; `EligiblePublicItem` has only the current eligible canonical `id`, `key`, `revision`, `kind`, `displayTextJa`, `displayTextVi`. For Users, `accessStatus:"unlocked"` means eligible access without a persisted Guest unlock, and `guestQuota`, `maxSaved` and `remaining` are `null` rather than a fabricated unlimited number. `savedCount` counts distinct currently saved canonical Items, including unavailable entries, until Unsave. Pagination includes both available and unavailable entries, so the FE never has to infer missing IDs from the total. Unavailable entries reveal no content, payload, media or private Rights information.

Existing public `GET /learning-paths` and `GET /learning-paths/{slug}` remain metadata-only discovery. The backend should expose objective metadata through a separate safe catalog projection where needed; the current full Lesson DTO must not be reused as a public preview. The exact public objective projection is outside this Guest mutation contract and requires FE/API integration review. Public `GET /skills/{type}/items` remains independent of Guest unlock. Skills detail/search/flashcard transport is outside JPN-011 and remains [pending in the main API contract](../../contracts/01-API-CONTRACT.md). An eligible Item appearing in Saved or a Lesson does not grant Lesson access.

## Database integrity — APPROVED INVARIANTS

- A stable server-issued Guest identity is distinct from the opaque browser credential and from `users`/`SPRING_SESSION`. Credential validation is server-side; store a non-reversible verifier, never the bearer value in plaintext application tables or logs. Guest data survives ordinary auth-session expiry and browser refresh while its identity remains valid.
- `last_active_at` is server-owned. An activity signal is accepted only after resolving a valid, non-expired Guest credential and CSRF session; no Guest ID or timestamp from the client is authoritative. The first active signal after Guest creation is persisted immediately. Draft write-throttling: after a persisted active signal, valid signals within five minutes return the persisted `lastActiveAt`/`retentionEligibleAt` without another database write; the first signal at or after that interval persists the current server time. To avoid cleanup or expiry earlier than 90 days after a qualifying signal within that window, calculate `retentionEligibleAt` and the server-side credential cutoff conservatively as persisted `last_active_at` plus 90 days plus at most the five-minute throttle window. This is a technical precision margin, not a visit limit or a change to the approved 90-day inactivity rule. An activity signal cannot alter unlocks, bookmarks, Assessment attempts, completion or mastery.
- **Draft credential renewal:** initialize the cookie with `Max-Age` of 90 days plus the five-minute precision margin from server issuance; issuance alone does not set `last_active_at` or count as active use. After each successfully persisted activity, send `Set-Cookie` with the same `Max-Age`, aligned to the new server-side cutoff. A throttled signal does not renew the cookie because its persisted activity timestamp has not changed. Before accepting or renewing any signal, the backend checks server-side validity (`created_at` before first activity, then the conservative `last_active_at` cutoff); an expired Guest cannot extend identity by sending a signal, even if its cookie is still present or cleanup has not run. The first real active use sends the signal and is persisted immediately. The credential and `SESSION` lifecycles stay independent. Cookie value rotation and deployment-specific SameSite/domain topology remain technical deployment details, not new retention rules.
- One unique `(guest, stable lesson identity)` unlock record represents access, independently of Path placement or Lesson revision. First unlock and daily usage increment commit atomically **before** full Lesson content can be served. The server calculates `Asia/Ho_Chi_Minh` calendar date; at most two distinct first unlocks per Guest/date. Concurrent requests with one slot remaining permit one new identity; concurrent requests for the same Lesson create one unlock/one usage. Old unlocks remain accessible on later days while Guest data remains valid.
- One unique `(actor, canonical Item identity)` bookmark record represents current Saved state across all Skills categories/contexts. A Guest's count is bounded by 20 transactionally; duplicate save is idempotent, remove frees capacity immediately, concurrent different-Item saves cannot exceed 20. Users have no product bookmark limit. Item revision changes do not create another bookmark slot.
- Authorization and quota decisions derive from the resolved actor and database state, not client counts, dates, `actorId`, station numbers or array positions. Rights/publication eligibility is checked again on every new content-bearing backend request and before a new unlock/bookmark save. Saved and unlock records never bypass live Rights checks. HTTP cache policy for content-bearing responses must reduce the risk of replaying material after revocation; previously downloaded bytes cannot be reliably recalled by the backend. Clients must not treat a previously received payload as a continuing authorization grant.
- Guest access, bookmarks, attempts and progress are stored server-side as separate concerns. Unlock, Lesson completion, official Assessment result, bookmark and Item mastery are not interchangeable. JPN-032/JPN-040 own their later persistence contracts.
- Cleanup eligibility follows 90 days after the latest active use. The draft five-minute write throttle requires the conservative cutoff above so a coalesced signal cannot cause early cleanup; throttling must not let an already expired identity become valid again. The qualifying activities and exclusions are the approved list above. Guest-to-account claim/merge/conflict rules remain **PENDING OWNER DECISION**. Cleanup job timing remains an implementation detail.

## Security and error contract — APPROVED

Guest credential and `SESSION` cookies must be sent only to the approved API origin; production must use HTTPS, `Secure`, HttpOnly, an approved SameSite/domain configuration, an explicit CORS origin allowlist and credentials. The Guest credential remains independent of the 30-minute Auth/CSRF session: a returning Guest with valid identity can establish a fresh CSRF session/token without losing server-side learning data. CSRF applies to every Guest mutation. Login's session-ID rotation and CSRF invalidation remain intact. Authenticated User precedence prevents a stale Guest cookie from exposing/mutating Guest records under a User session. A Guest may access only records linked to the server-resolved Guest identity; no caller-supplied actor ID is accepted. Direct independent and Path-contextual Lesson GETs check both live Rights/publication and unlock. Backend authorization is required for future Activity/Assessment reads under JPN-032. Saved reads return only eligible public fields or a minimal unavailable entry for Unsave; errors do not reveal private Rights reasons, other Guests or unpublished identities. New content-bearing requests must recheck live eligibility, and HTTP cache policy must reduce stale replay risk; already downloaded bytes cannot be recalled.

**Retention is separate from abuse controls:** JPN-011 records validated Guest activity and protects identity/data integrity. JPN-051 owns rate limiting, spam/bot defenses and any temporary cooldown, including any future `429`/`Retry-After` or backend-timed frontend countdown. This draft does not impose a visit, Back, Reload, Skills or Lesson revisit limit. The five-minute interval above throttles only activity database writes, not requests or access.

New error payloads use the implemented flat shape: `{ "code":"guest_unlock_quota_exceeded", "message":"Daily Lesson unlock limit reached." }`. These codes/statuses are approved technical contract responses in the current backend worktree. Actor routes use existing `401 unauthorized` when neither valid Guest nor User actor exists; Guest-only routes use `401 guest_identity_invalid`. Where content existence must remain private, the same generic `content_not_found` covers missing and ineligible resources.

| HTTP | Draft code | Case / FE handling |
|---|---|---|
| `400` | `invalid_request` / existing `invalid_content_query` | Malformed body, UUID or paging; do not mutate state. |
| `401` | `guest_identity_invalid` | Missing, invalid or expired Guest credential on Guest-only route; clear unusable cookie and offer explicit new Guest initialization. Existing User-only `/auth/me` keeps `unauthorized`. |
| `403` | `guest_unlock_quota_exceeded` | New Lesson would exceed today's two unlocks; return refreshed quota by a subsequent `GET /guest/quota`. |
| `403` | `lesson_not_unlocked` | Guest requests full eligible Lesson before first unlock; no full content. |
| `403` | `guest_bookmark_limit_reached` | New distinct save would exceed 20; existing save still succeeds. Re-read summary for current count. |
| `404` | existing `content_not_found` | Missing, unpublished, withdrawn or Rights-ineligible Lesson/Item/placement; do not distinguish causes publicly. |
| `409` | `actor_conflict` / `concurrent_operation_conflict` | User tries Guest initialization without claim policy, or a retriable concurrent write cannot be serialized. Server must not return 409 as a substitute for successful same-resource idempotent retry or an actual quota denial. |
| `503` | existing `content_unavailable` | Temporary database/content-read failure; no partial unlock/bookmark write or private details. |

## FE integration and acceptance test matrix

JPN-030 consumes catalog metadata plus `LessonAccess`, `GuestQuota` and `LessonUnlockResult`; it must not infer access from station order or a cached button state. JPN-035/036 consume canonical Item IDs and server `BookmarkSummary`, not a paginated list length; Vocabulary demo fields remain optional presentation adapter work, not new mandatory database columns. JPN-032 receives backend-gated access to official Assessment only after Guest unlock; Quick Check stays separate. JPN-040 receives distinct unlock/completion state. The frontend may send `POST /guest/activity` when a Guest actively opens/returns to the site or uses the approved views/interactions; it must not send retention signals from background polling, prefetch, token refresh, CSRF bootstrap or an idle tab. The frontend should refresh actor/quota/bookmark state after mutations or a stale cross-tab view, and never treat a prior payload as a Rights grant.
